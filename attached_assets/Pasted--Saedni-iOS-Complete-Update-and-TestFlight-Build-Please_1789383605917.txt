# Saedni iOS – Complete Update and TestFlight Build

Please implement a new production-ready iOS build of the existing Saedni application with all requirements below.

Work directly on the current project. Review the implementation first, then make the changes, test them, and prepare the new iOS build. Do not only provide recommendations or sample code.

## 1. Review and Safety Before Implementation

Before changing anything:

1. Review the existing codebase and architecture.
2. Review the database schema and relationships.
3. Review authentication and backend authorization.
4. Review customer registration, helper registration, request creation, contact, notification, completion, and profile flows.
5. Review the admin dashboard and existing filters.
6. Create a safe backup or restore point before running migrations.
7. Preserve all existing users, requests, contact records, preferences, and historical data.
8. Use safe and reversible database migrations.
9. Do not reset, replace, or delete the production database.
10. Do not introduce unrelated design or functionality changes.

---

# 2. Restrict the Service to Muscat

Saedni must operate only within Muscat Governorate.

Remove these location options from all new selections:

* صور
* صحار
* نزوى
* صلالة
* أخرى

Remove them from:

* Customer registration
* Helper registration
* Request creation
* Search and filters
* Customer profiles
* Helper profiles
* Profile editing
* Notification preferences
* Admin forms
* Every other location selector

Requirements:

* Keep all existing Muscat areas currently available in the application.
* Enforce the Muscat-only restriction on both the frontend and backend.
* Reject unsupported locations submitted directly through the API.
* Do not delete historical users or requests associated with locations outside Muscat.
* Mark unsupported locations as inactive and unavailable for new selections.
* Keep historical records using old locations visible in the admin dashboard.
* Remove “أخرى” only when it is a location option. Do not remove unrelated “أخرى” options used for service categories or other purposes.

# 3. Helper Service Areas

## New Helper Registration

Every new helper must:

* Select at least one service area within Muscat.
* Be allowed to select multiple service areas.
* Be prevented from completing registration without selecting an area.
* Receive a clear Arabic validation message when no area is selected.

## Existing Helpers

* Do not assign service areas automatically to existing helpers.
* If an existing helper has no saved service area, require them to select at least one Muscat area on their next login.
* Do not allow them to view available requests until they select and save at least one area.

## Helper Profile

Helpers must be able to:

* View their selected service areas.
* Add more Muscat service areas.
* Remove selected areas.
* Save changes from their profile.

A helper must always have at least one selected service area.

## Request Visibility

* Customers must select one specific Muscat area when creating a request.
* Helpers must only see requests belonging to one of their selected areas.
* Apply this filtering through backend/database queries, not only in the interface.
* Refresh the request list after a helper changes their selected areas.
* Prevent helpers from accessing out-of-area requests by manually changing an API request or request ID.
* Preserve the selected areas across sessions.

## Notifications

* Send request notifications only to helpers who selected the request’s area.
* Do not notify helpers about requests outside their service areas.
* Enforce notification targeting on the backend.

# 4. Record Helpers Who Contact Customers

Maintain a reliable backend record of every helper who contacts a customer through a request.

When a helper uses the phone or WhatsApp contact action, record:

* Request ID
* Helper ID
* Customer ID
* Contact method: phone or WhatsApp
* The contact number used
* Date and time of first contact
* Latest contact time, if needed

Requirements:

* Store contact events on the backend.
* Do not rely only on frontend or local device data.
* Confirm the helper is authorized to view the request before recording the contact.
* Prevent duplicate contacted-helper entries for the same helper and request.
* Repeated contact attempts may update the latest contact time but must not create duplicate list entries.
* If the required table or collection does not exist, create it with a safe database migration.
* Use these backend records to determine which helpers appear when the customer completes the request.

# 5. Display Contacted Helpers and Their Numbers

When displaying the contacted-helpers list, do not show only the helper’s name and contact method.

Every contacted-helper entry must display:

* Helper’s name
* Profile image, if available
* Contact method: phone or WhatsApp
* Actual contact phone number
* Average star rating
* Total number of ratings

Requirements:

* Display the contact number clearly below or beside the contact method.
* If the WhatsApp number differs from the regular phone number, display the number used for that contact method.
* Format Oman phone numbers consistently.
* Allow the customer to tap a phone number to start a call.
* Allow the customer to tap a WhatsApp number to open WhatsApp.
* Retrieve the number securely from verified helper profile data or the validated contact record.
* If no valid number is available, display a clear Arabic message instead of an empty field.
* Only the owner of the request and authorized administrators may view these numbers.
* Do not expose helper phone numbers in public profiles or unauthorized API responses.

# 6. Request Completion Flow

Implement this flow:

1. The customer chooses to complete their request.
2. The application retrieves the helpers who contacted the customer through that request.
3. The application displays each contacted helper’s name, image, contact method, contact number, average rating, and rating count.
4. The customer selects the helper who completed the work.
5. The customer rates the selected helper from 1 to 5 stars.
6. The application securely saves the selected helper and rating.
7. The request is marked as completed with help received.
8. The helper’s average rating and rating count are updated.

Only helpers with a valid backend contact record for that specific request may appear in the selection list.

## No Help Received

If helpers contacted the customer but no one completed the work:

* Display a “No help received” option.
* Allow the customer to close the request without selecting or rating a helper.
* Record the request as completed without help received.

If no helper contacted the customer:

* Allow the customer to close the request directly as “No help received.”
* Do not require a rating.

Process completion, helper selection, and rating safely so partial or inconsistent database records cannot be created.

# 7. Helper Rating System

The customer must be able to rate the selected helper using stars only.

Requirements:

* Use a rating scale from 1 to 5 stars.
* Do not include written comments or text reviews.
* Allow only one rating per request.
* Prevent duplicate rating submissions.
* Prevent helpers from rating themselves.
* Only the request owner can submit the rating.
* The selected helper must have contacted the customer through that request.
* Validate all rules on the backend.
* Store the star value as an integer from 1 to 5.
* Recalculate the helper’s average rating and total rating count after every valid rating.

Store:

* Unique rating ID
* Request ID
* Customer ID
* Helper ID
* Star value
* Creation date and time

Add a database-level unique constraint, where supported, to ensure only one rating can exist for each request.

Do not trust customer IDs, helper IDs, ownership, or eligibility received only from the frontend. Verify everything from authenticated backend data.

A submitted rating must not be editable or submitted again unless the existing admin system already has an authorized correction process.

# 8. Display Helper Ratings

Display each helper’s average star rating and total rating count:

* In the contacted-helpers list
* In the helper’s profile
* Wherever helper information is already displayed to customers without requiring an unrelated redesign

Use a consistent format such as:

`★ 4.8 (12)`

If the helper has no ratings, display:

`جديد`

or:

`لا توجد تقييمات بعد`

Do not display written reviews.
